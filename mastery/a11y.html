4.1 无障碍深入：键盘、焦点与播报 ​

漫画引入 ​

小 R：我用 div 做了个下拉菜单，鼠标点着挺顺，测试同学说 Tab 进不去、Esc 也关不掉。

老 S：你重写的是 Radix 已经写好的 200 行键盘逻辑。菜单不是「点击后显示一个盒子」，它是一个有角色、有焦点管理、有方向键的系统。

小 R：那我用 Radix 就自动无障碍了？

老 S：它负责 80%，剩下的 20% 是标签、文案、播报和对比度——这些只有你知道。

学习目标 ​

  • 理解 Radix 自动提供的无障碍能力边界。
  • 掌握焦点可见、焦点归还、焦点陷阱的行为与验证方法。
  • 会给动态内容加 aria-live 播报。
  • 会用键盘完整走查一个页面，并修掉最常见的五类问题。

概念讲解 ​

Radix 已经做了什么 ​

能力具体表现
角色与状态role="dialog"、aria-expanded、aria-controls、data-state
焦点陷阱Dialog / Popover 打开后，Tab 不会跑到背景
焦点归还关闭后焦点回到触发元素
方向键Menu、Select、Tabs、Accordion 的上下左右与 Home/End
类型搜索Select / Menu 输入字母跳转
关闭语义Esc、点击遮罩、外部点击
滚动锁定Dialog 打开时禁止背景滚动

这些不需要你写，也不应该重写。你要做的是别破坏它：不要给 Radix 触发器外面再包一层 onClick 的 div，不要手动 focus() 打架。

焦点可见 ​

tsx
<button className="focus-visible:ring-3 focus-visible:ring-ring/50 outline-none">
  • 用 :focus-visible 而不是 :focus：鼠标点击不显示焦点环，键盘导航显示。
  • 永远不要 outline: none 而不给替代样式。
  • 焦点环至少 2px，和背景有足够对比。

焦点归还 ​

Dialog 关闭后，焦点应该回到「打开对话框」按钮。Radix 通过 DialogTrigger 记录触发元素。如果你用受控模式、没有 trigger，就要自己保存 document.activeElement：

tsx
const triggerRef = useRef<HTMLElement | null>(null)

function open() {
  triggerRef.current = document.activeElement as HTMLElement
  setOpen(true)
}

function close() {
  setOpen(false)
  triggerRef.current?.focus()
}

可读名称 ​

图标按钮必须二选一：

tsx
<Button size="icon" aria-label="删除项目"><Trash2 /></Button>

{/* 或者用 sr-only 文本 */}
<Button size="icon">
  <Trash2 />
  <span className="sr-only">删除项目</span>
</Button>

Tooltip 不能替代可读名称：它不可聚焦，读屏用户也不会主动去读。

aria-live 播报 ​

视觉上的数字变化，读屏用户感知不到。加一个 live region：

tsx
<div aria-live="polite" aria-atomic="true" className="sr-only">
  {announcement}
</div>
  • polite：等当前朗读结束再播，适合大多数状态更新。
  • assertive：立即打断，只用于错误、紧急中断。
  • aria-atomic="true"：整段重读，而不是只读变化的部分。
  • region 必须常驻 DOM。动态插入一个 live region 往往不会被播报。

错误与表单 ​

tsx
<p role="alert" className="text-destructive">邮箱格式不正确</p>
  • role="alert" 等价于 aria-live="assertive"，适合校验错误。
  • 输入框加 aria-invalid 与 aria-describedby 指向错误文本。
  • 错误出现时把焦点移到第一个错误字段，长表单尤其重要。

键盘走查清单 ​

  1. 只用 Tab，能否到达所有交互元素？顺序是否与视觉一致？
  2. 焦点框是否始终可见？
  3. Enter / Space 是否激活按钮？
  4. 浮层打开后，Tab 是否被限制在浮层内？
  5. Esc 是否关闭浮层并把焦点还回去？
  6. 菜单方向键、Home/End 是否工作？
  7. 是否能用键盘完成一次完整任务（如提交表单）？

bash

页面包含：

  • 跳转到主要内容的 skip link（按 Tab 第一个出现）
  • Dialog 焦点陷阱与归还

  • aria-live 计数播报

常见坑 FAQ ​

Q：Tab 键顺序和视觉顺序不一致？

DOM 顺序决定 Tab 顺序。不要用 tabIndex 正数去「修」，应该调整 DOM 结构或用 CSS 布局。

Q：aria-label 写了但读屏还是读「按钮」？

检查是否写在了子元素上，或者被 aria-hidden 的父级遮住。用 DevTools 的 Accessibility 面板看计算后的名称。

Q：Dialog 关闭后焦点丢了？

可能手动卸载了触发元素（如条件渲染），或用了非受控的 open 且没有 trigger。保存触发元素引用，关闭后显式 focus()。

Q：live region 不播报？

region 必须在更新前就存在；display: none 会阻止播报，用 sr-only（视觉隐藏但仍在无障碍树中）。

Q：颜色对比度怎么快速检查？

Chrome DevTools → Elements → Accessibility → Contrast。正文 4.5:1，大字号 3:1。半透明文字要叠加背景后计算。

Q：自动化测试能覆盖多少？

axe 能查出一部分结构性错误（缺 label、角色不匹配），但查不出「Tab 顺序是否合理」「文案是否可理解」。键盘走查不能省。

练习与延伸 ​

  1. 给 13-a11y 的计数器加 role="status"，对比与 aria-live="polite" 的差异。
  2. 故意删掉 Dialog 的 DialogTitle，用读屏或 Accessibility 面板观察后果。
  3. 用 axe DevTools 扫描示例页，修掉所有 serious 级问题。
  4. 给项目加一条 CI 检查：关键页面跑 axe-core。
  5. 阅读 Radix Accessibility 文档 与 WAI-ARIA Authoring Practices。
