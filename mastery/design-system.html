4.3 设计系统落地：Token、变体与分层 ​

漫画引入 ​

小 R：产品要我做一个「已上线」的绿色标签，我直接写了个 bg-green-100 text-green-700。两周后发现全站有 14 种绿色。

老 S：因为你每次都从头做决定。设计系统的工作，是让决定只发生一次。

小 R：那是不是要维护一个超大的组件库？

老 S：先维护 token 和变体。组件是结果，不是起点。

学习目标 ​

  • 建立四层结构：Token → Primitive → Pattern → Feature。
  • 用 cva 定义可组合的变体，而不是堆 props 分支。
  • 把颜色、圆角、排版收敛为可枚举的标尺。
  • 知道设计系统该由谁维护、如何演进。

概念讲解 ​

四层结构 ​

层级内容改动成本负责人
L1 TokenCSS 变量：颜色、圆角、字号、间距低设计 + 前端
L2 PrimitiveButton、Input、Badge 等原语中前端
L3 PatternStatusPill、ConfirmDialog 等组合中前端
L4 Feature业务页面与数据高业务团队

规则：上层可以依赖下层，下层不能反向依赖上层。业务页面不直接写颜色值，也不重新发明按钮。

Token 的命名 ​

语义优先，而不是色号：

css
/* 好 */
--primary
--muted-foreground
--destructive

/* 不好 */
--blue-600
--gray-100

同一个蓝色可能用于主按钮、链接、选中态，它们的语义不同。按用途命名，主题切换和暗色适配才有意义。

用 cva 定义变体 ​

tsx
const statusPillVariants = cva(
  'inline-flex items-center gap-1.5 rounded-full border font-medium',
  {
    variants: {
      tone: {
        neutral: 'border-border bg-muted text-muted-foreground',
        success: 'border-emerald-500/20 bg-emerald-500/10 text-emerald-700 dark:text-emerald-300',
        warning: 'border-amber-500/25 bg-amber-500/10 text-amber-700 dark:text-amber-300',
        danger: 'border-destructive/20 bg-destructive/10 text-destructive',
      },
      size: {
        sm: 'px-2 py-0.5 text-[11px]',
        md: 'px-2.5 py-1 text-xs',
      },
    },
    defaultVariants: { tone: 'neutral', size: 'md' },
  },
)

优势：

  • 变体是有限集合，不会出现「第 15 种绿色」。
  • 类型自动推导，写错 tone 会在编译期报错。
  • cn() 合并时，消费方的 className 优先级最高。

变体的维度控制 ​

不是所有组合都合理。例如 Button 的 size="icon" 只应该配图标内容。用类型或注释约束：

tsx
type ButtonProps = VariantProps<typeof buttonVariants> & {
  /** icon 尺寸下请只放一个图标 */
  size?: 'default' | 'sm' | 'lg' | 'icon'
}

变体爆炸时，先问「这个维度真的需要吗」。两个维度 5×4=20 种，已经很难测完。

间距与排版标尺 ​

tsx
// 标尺内
<div className="space-y-4 p-6">
<h2 className="text-xl font-semibold">
<p className="text-sm leading-6 text-muted-foreground">

// 随意值
<div style={{ marginTop: 13, padding: 18 }}>

设计稿的 13px 应该先问能不能对齐 12/16。长期看，标尺比精确还原更重要，否则每个页面都在微调。

设计系统如何演进 ​

  1. 从真实页面里长出来：先有 3 个页面，再有 token，再有组件。
  2. 变更走提案：改 token 影响全站，不能某人在业务 PR 里顺手改。
  3. 用示例页验证：每个组件至少一个可运行示例，改完跑一遍。
  4. 保留 deprecation 期：旧变体标记废弃，下一 major 再删。
  5. 文档即契约：什么场景用哪个变体，写在示例旁边。

StatusPill 源码见 src/components/status-pill.tsx：

tsx
export function StatusPill({ className, tone, size, dot = true, children, ...props }: StatusPillProps) {
  return (
    <span className={cn(statusPillVariants({ tone, size }), className)} {...props}>
      {dot && <span className="size-1.5 rounded-full bg-current opacity-70" />}
      {children}
    </span>
  )
}

常见坑 FAQ ​

Q：Token 越加越多怎么办？

每加一个 token 都要回答「它和现有 token 的区别是什么」。区分不了就复用。定期清理未使用的变量。

Q：业务方要求「就改这一次」的颜色怎么办？

用一次性类（如 text-emerald-600）并注明原因，不要进 token。出现第三次再提升为 token。

Q：cva 和 Tailwind 的 @apply 怎么选？

cva 输出类名字符串，保留「就地看到样式」的优势；@apply 把样式藏进 CSS。组件变体用 cva，全局基础样式才用 @apply。

Q：暗色模式要不要每个组件单独适配？

不需要。只要组件用语义 token，暗色在 token 层解决。需要单独适配的只有图片、阴影和半透明遮罩。

Q：设计系统要不要做成 npm 包？

跨项目复用才需要。单项目内，src/components + 示例页就够了，过早打包会增加发布成本。

Q：怎么防止有人绕过设计系统？

ESLint 限制业务目录直接使用原始色阶类，CI 跑示例页视觉回归。工具约束比口头约定有效。

练习与延伸 ​

  1. 给 StatusPill 增加 info 之外的 brand tone，并从 --primary 派生颜色。
  2. 把 Button 的变体矩阵整理成一张「什么时候用哪个」的表格。
  3. 在示例页加一个 spacing 标尺 Tab。
  4. 用 Playwright 给组件示例页截屏，做一次视觉回归。
  5. 下一章：把组件库打包、发版并让消费方正确接入。
