4.4 组件库发布：从源码到可安装的包 ​

漫画引入 ​

小 R：我把 src/components 直接发到 npm 了，同事装完报错「Invalid hook call」，还说样式全丢。

老 S：两件事：你把 React 打进了包，而且没有告诉消费方 token 从哪来。

小 R：那正确姿势是什么？

老 S：库模式构建、依赖外置、明确的 exports、以及一份能照着跑的接入文档。

学习目标 ​

  • 用 Vite lib 模式打包组件库，产出可发布的 ESM 产物。
  • 理解 external 与 peerDependencies 的配合，避免重复 React 实例。
  • 正确配置 exports、files、sideEffects。
  • 建立发布前检查清单与版本策略。

概念讲解 ​

构建：lib 模式 ​

ts
export default defineConfig({
  plugins: [react(), tailwindcss()],
  build: {
    lib: {
      entry: path.resolve(import.meta.dirname, 'src/lib/index.ts'),
      name: 'RadixKit',
      fileName: 'radix-kit',
      formats: ['es'],
    },
    rollupOptions: {
      external: ['react', 'react-dom', 'react/jsx-runtime', 'radix-ui', 'class-variance-authority', 'lucide-react'],
    },
  },
})

产物只有一个入口文件（及其 sourcemap），没有 index.html，也不做代码分割。适合组件库；应用仍然用默认的 SPA 构建。

为什么要 external ​

如果 react 被打进包里，消费方的应用会同时存在两份 React：

  • Hooks 报 Invalid hook call。
  • Context 不共享，主题、i18n 全部失效。
  • 包体积翻倍。

external 告诉 Rollup「不要打包，保留 import」，peerDependencies 告诉包管理器「由使用方提供」。两者必须成对出现。

package.json ​

json
{
  "name": "@acme/radix-kit",
  "type": "module",
  "main": "./dist/radix-kit.js",
  "module": "./dist/radix-kit.js",
  "files": ["dist"],
  "exports": {
    ".": { "import": "./dist/radix-kit.js" }
  },
  "sideEffects": false,
  "peerDependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  }
}
  • exports 决定消费方能 import 什么。只暴露入口，内部路径不可达。
  • files 控制发布内容，避免把 src、测试、示例发上去。
  • sideEffects: false 让打包器放心 tree-shake。若组件有全局副作用（如注入 CSS），要显式列出文件。

Webpack 等旧工具可能不读 exports，main / module 作为兼容字段保留。

样式策略 ​

两条路线：

策略做法优点缺点
随包发 CSS构建时产出 style.css，消费方 import接入简单定制难，token 固定
只发类名消费方配置 Tailwind 扫描本包可定制主题需要文档与配置

无论哪种，都要提供 token。否则 bg-background 在消费方不存在，组件会是无色的。常见做法是导出一份 theme.css，消费方在自己的 Tailwind 入口里 @import。

类型声明 ​

示例为了聚焦体积没有产出 .d.ts。生产库建议加 vite-plugin-dts，或单独跑 tsc --emitDeclarationOnly：

json
{
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  }
}

没有类型，TypeScript 消费方只能得到 any，组件库的价值会打折。

发布前检查 ​

bash
pnpm build
pnpm pack            # 生成 tarball，检查内容
npm publish --dry-run

再建一个干净项目，真实安装 tarball：

bash
pnpm add ../acme-radix-kit-0.1.0.tgz

跑一次真实的 import、渲染、暗色切换。这一步能发现 90% 的「本地好好的，装了就坏」。

版本策略 ​

  • patch：修样式、修 bug，API 不变。
  • minor：新增组件、新增可选 prop。
  • major：删除组件、改变默认行为、改动 token 名称。

CHANGELOG 写「为什么」而不只是「改了什么」。破坏性变更给出迁移代码。

可运行示例 ​

完整页面见 examples/16-publish。

bash
cd examples/16-publish
pnpm install
pnpm dev      # 预览 App
pnpm build    # 库模式构建
ls dist       # radix-kit.js + sourcemap

示例的 src/lib/index.ts 是唯一公开入口：

ts
export { Button, buttonVariants } from '@/components/ui/button'
export { Badge, badgeVariants } from '@/components/ui/badge'
export { Card, CardHeader, CardContent, CardFooter } from '@/components/ui/card'
export { StatusPill, statusPillVariants } from './status-pill'
export { cn } from '@/lib/utils'

构建产物约 8KB（gzip 2KB），因为 React、Radix、lucide 全部外置。

常见坑 FAQ ​

Q：消费方报 Invalid hook call？

包里打进了第二份 React。检查 external 是否包含 react 与 react/jsx-runtime，peerDependencies 是否声明。

Q：组件装上了但没有样式？

类名是有的，但消费方没有对应的 Tailwind 配置或 token。按「样式策略」二选一，并把配置写进 README。

Q：exports 配了，旧项目还是 import 不到？

旧打包器可能不认 exports。补 main / module 字段；或让消费方升级构建工具。

Q：sideEffects: false 会不会误删样式？

若包里通过 import './style.css' 注入全局样式，需要把该文件列进 sideEffects 白名单，否则会被 tree-shake。

Q：可以用 tsup 吗？

可以。tsup 对库场景更省配置，Vite 的优势是与示例应用共用一套插件。团队统一即可，不必两个都用。

Q：私有 registry 怎么发？

在 .npmrc 配置 scope 与 registry 地址，npm publish --registry=...。CI 里用只读 token 安装、发布 token 单独管理。
