4.5 性能与体积优化 ​

漫画引入 ​

小 R：页面一打开就卡三秒，我看了一圈组件，每个都挺简单的啊。

老 S：组件简单不等于页面轻。你一次渲染了 2000 行，还在每次输入时重新过滤一遍。

小 R：那我把所有组件都包上 memo？

老 S：那只会让代码更复杂。先测量，再决定是少渲染、少计算，还是少加载。

学习目标 ​

  • 建立性能问题的分类：渲染、计算、加载、体积。
  • 会用 useMemo / memo / React.lazy / content-visibility 处理不同瓶颈。
  • 读懂构建产物的体积报告，定位大依赖。
  • 知道什么时候优化是无效的，以及如何验证优化有效。

概念讲解 ​

四类问题，四种手段 ​

症状原因手段
输入卡顿每次按键都做重计算useMemo、防抖、下放状态
滚动掉帧DOM 太多虚拟化、content-visibility、分页
首屏慢初始包太大路由分割、React.lazy、依赖外置
交互延迟无关组件跟着重渲染memo、稳定的 props、状态下放

先定位再优化。没有测量的优化，大概率是在给错误的地方加 memo。

计算缓存 ​

tsx
const filtered = useMemo(() => {
  const query = keyword.trim().toLowerCase()
  return query ? rows.filter((row) => row.name.includes(query)) : rows
}, [keyword])

依赖数组写全。漏依赖会拿到旧值，多写依赖会让缓存失效。

对于 2000 条以内的筛选，useMemo 足够。真正的大数据量应该放到 Web Worker 或服务端。

记忆化组件 ​

tsx
const MemoChild = memo(function MemoChild() {
  return <Badge>...</Badge>
})

memo 只在 props 浅比较相等时跳过渲染。如果每次父组件都传新的对象 / 函数，memo 等于没加：

tsx
// 每次渲染都是新对象，memo 失效
<Child options={{ pageSize: 10 }} />

// 稳定引用
const options = useMemo(() => ({ pageSize: 10 }), [])

React 19 的编译器可以自动做一部分记忆化，但不要依赖它来掩盖结构问题。状态下放到真正需要的组件，往往比 memo 更有效。

延迟加载 ​

tsx
const HeavyPanel = lazy(() => import('@/components/heavy-panel'))

{showHeavy && (
  <Suspense fallback={<Spinner />}>
    <HeavyPanel />
  </Suspense>
)}
  • 只有用户可能用到的重面板才值得拆 chunk。
  • 拆分过细会产生大量小请求，HTTP/2 下问题不大，但首屏关键路径别拆。
  • lazy 只解决下载，不解决渲染成本。

视口裁剪 ​

tsx
<div className="[content-visibility:auto] [contain-intrinsic-size:40px]">
  • content-visibility: auto 让浏览器跳过屏幕外内容的渲染。
  • contain-intrinsic-size 给一个占位高度，避免滚动条跳动。
  • 它不是虚拟化，DOM 仍然存在；几千行以上还是建议虚拟列表。

体积审计 ​

bash
pnpm build
# 或接入 rollup-plugin-visualizer

看三件事：

  1. 最大的 chunk 里有什么。常见大头：图表库、日期库、图标全量导入、Radix 全量包。
  2. 是否有重复依赖（两份 React、两份日期库）。
  3. 首屏是否加载了后台页面才用的代码。

图标与 Radix 的导入 ​

tsx
// 推荐：按名导入
import { Check, Copy } from 'lucide-react'

// 避免：整包
import * as icons from 'lucide-react'

radix-ui 统一包在 tree-shaking 正常时不会全量进入产物，但构建配置异常（如 CJS 互操作）可能导致整包被打入。体积报告里看到异常大的 chunk，先查这里。

验证优化有效 ​

  • 用 React DevTools Profiler 记录一次交互，看 commit 次数与耗时。
  • 用 Chrome Performance 录制滚动，看是否掉帧。
  • 用 vite build 的前后体积对比。
  • 在低端机与 4G 网络下测，而不是只测开发机。

可运行示例 ​

完整页面见 examples/17-perf。

bash
cd examples/17-perf
pnpm install
pnpm dev

页面包含四个实验：

  1. 计算缓存：2000 行数据 + 关键词筛选，观察输入流畅度。
  2. 记忆化：点击按钮触发父组件重渲染，对比普通子组件与 memo 子组件的渲染次数。
  3. 延迟加载：按需加载 40 行的分析面板，构建后可见独立 chunk。
  4. 体积清单：上线前的八条检查项。

关键片段：

tsx
const HeavyPanel = lazy(() => import('@/components/heavy-panel'))

<Suspense fallback={<p>正在加载 chunk…</p>}>
  <HeavyPanel />
</Suspense>

构建输出里会出现独立的 heavy-panel-*.js，说明拆分生效。

常见坑 FAQ ​

Q：加了 memo 还是每次渲染？

props 里有新对象 / 新函数，或组件被放在会重新挂载的位置。先检查引用稳定性。

Q：useMemo 让代码更慢了？

小计算加 useMemo 反而增加比较成本。只在计算明显较重、或结果被下游依赖时使用。

Q：content-visibility 导致搜索定位失败？

浏览器 Ctrl+F 通常能处理，但自定义滚动定位可能算错高度。用 contain-intrinsic-size 提供近似值。

Q：为什么开发模式很慢？

StrictMode 会双调用渲染，开发构建也未压缩。性能结论以生产构建为准。

Q：拆包后首屏没变快？

可能拆的是首屏关键路径，或拆出来的 chunk 仍然在首屏请求。检查 Network 瀑布图。

Q：要不要上虚拟列表？

行高固定、数据量大于 1000 时值得。行高不定会增加复杂度，先用分页或 content-visibility 过渡。

练习与延伸 ​

  1. 把 17-perf 的数据量调到 10000 条，对比有无 useMemo 的输入延迟。
  2. 给 MemoChild 传一个 useCallback 包裹的函数，验证 memo 是否恢复生效。
  3. 接入 rollup-plugin-visualizer，找出最大的三个依赖。
  4. 用 React DevTools Profiler 记录一次筛选交互，标出耗时最长的组件。
  5. 阅读 React 性能文档 与 web.dev 的 content-visibility。
