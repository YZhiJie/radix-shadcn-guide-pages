3.3 组件二次封装 ​

漫画引入 ​

小 R：我在每个页面都写了一遍「打开弹窗 → 确认 → 调接口 → 关闭 → 报错」，第七次复制的时候手抖删错了行。

老 S：你不是在写页面，你是在重复实现同一个状态机。把它收进一个 ConfirmDialog。

小 R：那会不会把 Radix 的能力封死？

老 S：取决于你怎么封。保留 props 透传和 className，封装的是流程，不是限制。

学习目标 ​

  • 判断什么时候该封装、什么时候该直接用原语。
  • 掌握三种常见封装：流程型（ConfirmDialog）、装饰型（IconTip）、配置型（ActionMenu）。
  • 学会保留逃生口：asChild、props 透传、className 覆盖。
  • 理解受控与非受控两种 API 的取舍。

概念讲解 ​

封装的是「重复的决策」 ​

看到一个模式出现第三次，再抽象：

重复内容封装产物收益
弹窗 + 加载 + 错误 + 关闭ConfirmDialog调用方只写 onConfirm
图标按钮 + 提示 + aria-labelIconTip无障碍不靠记忆
菜单 + 分隔符 + 危险项分组ActionMenu菜单由数据描述
卡片 + 状态徽标 + 操作区EntityCard列表页统一结构

第一次直接写原语，第二次复制，第三次才抽象。过早封装会把还没定型的交互锁死。

流程型封装：ConfirmDialog ​

核心是把异步状态收进组件：

tsx
async function handleConfirm() {
  setPending(true)
  setError(null)
  try {
    await onConfirm()
    setOpen(false)
  } catch (cause) {
    setError(cause instanceof Error ? cause.message : '操作失败')
  } finally {
    setPending(false)
  }
}

三个细节决定它好不好用：

  1. pending 期间禁止关闭，避免请求还在飞、弹窗已经没了。
  2. 错误留在弹窗内，用户可以直接重试，而不是关掉再找入口。
  3. 关闭后焦点回到触发元素——这一点由 Radix Dialog 保证，不要自己 focus()。

受控与非受控 ​

默认用法给 trigger，组件自己管理 open：

tsx
<ConfirmDialog
  trigger={<Button variant="destructive">删除</Button>}
  title="删除项目？"
  description="此操作不可撤销。"
  onConfirm={removeProject}
/>

从菜单项触发时，没有合适的 trigger 元素，就传 open 切到受控模式：

tsx
<ConfirmDialog
  open={Boolean(deleting)}
  onOpenChange={(next) => !next && setDeleting(null)}
  title="删除项目？"
  description="从 ActionMenu 触发的删除。"
  onConfirm={handleDelete}
/>

两种模式共用同一份内容与状态逻辑，比写两个组件更划算。

装饰型封装：IconTip ​

tsx
<Button variant="ghost" size="icon" aria-label={label}>
  {children}
</Button>

要点：

  • aria-label 给读屏，Tooltip 给视觉用户，两个都要。
  • TooltipProvider 放在应用根部更好，避免每个图标都创建 provider。
  • Tooltip 不能承载关键信息，它不可聚焦、不可选中。

配置型封装：ActionMenu ​

tsx
<ActionMenu
  label="更多操作"
  items={[
    { label: '重命名', icon: Pencil, onSelect: rename },
    { label: '归档', icon: Archive, onSelect: archive, hidden: isArchived },
    { label: '删除', icon: Trash2, onSelect: remove, destructive: true },
  ]}
/>

把「分隔符插在哪、危险项放最后」变成约定，调用方只关心动作清单。hidden 让权限控制也能在数据层解决。

保留逃生口 ​

  • 组件的 props 继承原始元素类型：ComponentProps<typeof Button>。
  • className 永远追加而不是替换，用 cn() 合并。
  • 需要换元素时用 asChild，而不是加一堆 as 分支。
  • 不在封装层写死业务文案，标题、描述、按钮文字都从 props 传入。

常见坑 FAQ ​

Q：封装后想改按钮样式怎么办？

先看 className 是否能覆盖。若不行，说明组件内部用了 !important 或硬编码样式，应该改成 cn(default, className)。

Q：asChild 和直接传 children 有什么区别？

asChild 会把 Radix 的行为与 ARIA 属性合并到你的子元素上，不额外生成 DOM。传 children 只是内容，触发器仍是 Radix 默认元素。

Q：Dialog 里再开 Dialog 可以吗？

可以，但焦点栈会变复杂。多数场景应该用「关闭当前 → 打开下一个」或内联确认，而不是嵌套弹窗。

Q：为什么错误提示不用 toast？

确认类操作需要「失败后立即重试」，弹窗内错误更贴近操作。toast 适合成功通知或后台任务。

Q：封装组件要不要写 Storybook？

如果组件会被多个团队使用，值得。只有自己项目用，一个示例页面加注释就够。

练习与延伸 ​

  1. 给 ConfirmDialog 加 requireText：必须输入项目名才能确认删除。
  2. 把 ActionMenu 的 items 支持分组（group: 'danger'），自动生成小标题。
  3. 写一个 EntityCard，统一「标题 + 状态 + 描述 + 行操作」的列表项。
  4. 阅读 Radix 的 Composition 指南。
